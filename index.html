Overview

The one question

Where, and why, does an embodied agent's performance degrade along a chain of dependent tasks? HospitalBench 2027 is a workshop and challenge on ten simulated hospital tasks of chained sub-tasks, each link checked by moving the previous result.

Beside end-task success, every entry gets a failure-mode profile read from its logged trajectories: compounding errors per link, recovery, state drift (the pose a robot reports against its true pose) and tool-use breakdowns, with per-position curves and task-length scaling.

Two tracks, foundation models and vision-language-action (VLA) policies, are scored per sub-task and per link. Harm events are simulator proxies, not injuries.

A chain, filmed

Format

  • Workshop: half-day, in person, with remote invited talks over the CVPR Zoom room.
  • Challenge: one challenge on the ten tasks, with two tracks.

The Ten Tasks

Robot and simulator

A wheeled mobile manipulator (Ridgeback base, 7-DoF Franka arm, parallel gripper opening to 8 cm, head and wrist cameras) in NVIDIA Isaac Sim. Each task has its own floor plan, furnished with NVIDIA SimReady assets. Each sub-task instruction states its pass terms in numbers (position and heading bands, a hold time), checked from simulator state. Simulated staff and visitors cross the work area on schedules; the robot must keep clear.

Build status, 3 November 2026

  • All ten rooms are built in Isaac Sim, with 2 public start states per task, and pass a physics settle check.
  • The scripted reference robot completes sub-tasks 1 to 5 as one chain on both start states for T1, T7, T9 and T10; on the other six tasks, early sub-tasks only.
  • One link of 40 is certified so far, T1.01→T1.02.

Tracks

Ten tasks, two tracks, one scoring. Every entry, trained or foundation model, is called through an API by the same harness, so participant scores sit on one leaderboard beside OpenAI, Anthropic Claude and Google Gemini models evaluated the same way.

Track 1: foundation models through API calls

The agent receives each sub-task instruction and images from the head and wrist cameras. It acts through six calls:

  • drive the base to a pose;
  • move the fingertip to a 6-DoF pose;
  • set the gripper opening;
  • turn the head camera;
  • wait;
  • end the sub-task.

The world is paused between calls; each sub-task has a cap on calls, published on the task cards before 1 February 2027. Prompting, memory and the tool loop are free, but every robot call must be chosen by the model: no hand-written controllers or stored poses for the ten tasks. A Track 1 team submits its agent plus an API key for a hosted foundation model. Evaluation runs on EvalAI remote evaluation with the organizers' GPU as the worker, which runs the simulator only; scores post automatically to the leaderboard. A team may optionally duplicate the public Hugging Face Space (Isaac Sim, harness and scorer) to a paid GPU of its own to develop on the public start states. Entrants pay their own API use.

Track 2: trained VLA policies

The policy receives the instruction, camera images and robot state, and outputs, at 10 Hz, base velocity (vx, vy, yaw rate), 7 arm joint position targets and the gripper width. Entrants host their trained policy behind an API endpoint (for example a Hugging Face Inference Endpoint or any provider). Our harness calls it once per control step and gets the action back. The world pauses between calls, so network latency does not change scores; the same call cap per sub-task applies. The organizers' worker runs the simulator only, with no inference GPU, and entrants pay their own endpoint costs. Any training data may be used except test and reserve start states.

The demonstration set holds 100 scripted-robot demonstrations per task on development start states (images, robot state, actions, instructions), recorded by 1 February 2027. Track 2 has no trained baseline yet.

How an entry is scored

Episodes

Every test start state is run as a chained episode, the five scored sub-tasks in order, ending at the first failure. It is run twice: clean, and with one organizer-applied displacement inside the band of a position or heading link; entrants know such displacements happen, but not where.

Link-alone episodes: for each link k→k+1, every test state also starts from the scripted reference robot's end state of sub-task k, displaced the same way, so every link cell has at least 5 displaced episodes whatever the entry did earlier. They are reported apart from the chained runs.

Metrics

  • Per sub-task: the share of clean episodes that pass sub-task k among those that passed sub-tasks 1 to k−1.
  • Per link: the pass rate of k+1 in chained displaced episodes and in link-alone episodes, beside its clean rate; the gap shows whether the entry acts on the actual or the intended result of k. Counts accompany every rate.
  • End-task success: the share of episodes that pass all five scored sub-tasks, one reported number beside the per-step scores.
  • Failure-mode profile (per entry, beside the ranking score, never merged into it): compounding, recovery, state drift, tool-use breakdowns (Track 1), and the share of episodes passing the first k sub-tasks, with task-length scaling. A cell with fewer than five episodes prints “too few”.
  • Harm events: shown beside every chain score, zeros included; each fails its task, and none is an injury.

Ranking score

The ranking score is the mean number of sub-tasks passed in order, divided by five, over the clean test episodes of all tasks. End-task success and the ranking score come from chained runs only. No baseline is above zero end-task success today (0 of 35 pilot runs), so at this floor the ranking score ties at or near 0. Scores that agree to two decimals are ranked by the number of episodes passing each sub-task, deepest position first, then the unrounded mean, then lower mean cost per run (Track 1 API dollars) or, for Track 2, fewer model calls per episode. The leaderboard also shows per-area and per-kind breakdowns.

Every link is certified before release

For each link from sub-task k to k+1, the organizers' scripted reference robot completes sub-tasks 1 to k on a development start state, then k's result is moved inside its own pass band in every planar direction, at two sizes fixed in advance, with a simulated person far from the work area and crossing it. The link is accepted only if a blind replay of the reference plan fails in every displaced run and an adaptive reference passes in every one. For T1.01→T1.02 the adaptive reference passed 32 of 32 displaced runs and the blind replay 0 of 32. Certificates are published with the task cards.

Preventing cheating

Test and reserve start states are never released as files; entrants' models see them only as camera images during organizer-run episodes (Track 1 through the entrant's own API account, Track 2 at its endpoint). Each team has one scored test submission and one final submission, also run on the reserve split. The never-revealed reserve split, the final rerun and a code check on request guard the final ranking; for a code check of a hosted model, the team shares weights and inference code with the organizers privately on request. An entry that cannot be reproduced, breaks a rule, or scores lower on reserve than on test by more than a published threshold is re-ranked. Organizers' groups may submit but win no awards.

Ethics and Licenses

A high score in a simulated hospital is not evidence that a robot is safe near patients; real deployment needs clinical validation and regulatory review. No task touches a patient, and harm events are proxy tests on simulator state, not injuries.

All data are simulated: no real person, patient record or hospital is recorded, and names and record numbers on labels are invented. SimReady assets are CC BY 4.0 and our release credits NVIDIA. Tasks, scenes and demonstrations are released under CC BY 4.0, the scorer and code under the MIT license.
